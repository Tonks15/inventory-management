Factory Inventory Management System

A full-stack demo: a Vue 3 single-page dashboard backed by a FastAPI service that serves in-memory data loaded from JSON files. There is no database.

Architecture Tech stack Data flow API surface Code layout Known gaps

System architecture

Three tiers, all running locally. The browser talks to the API over HTTP; the API never touches a database.

Data flow

What happens when a user changes a filter on the dashboard.

  1. User changes a filterFilterBar updates shared refs in useFilters: period, warehouse, category, status. State is a module-level singleton, so every view sees it.
  2. View watches the filtersA watch in the view (for example Dashboard.vue) fires and calls getCurrentFilters(). The period value is sent as month.
  3. api.js builds the requestFilters equal to all are dropped. Remaining values become query params on http://localhost:8001/api/....
  4. FastAPI filters in memoryThe route handler runs apply_filters and filter_by_month over the Python lists. Quarters such as Q3-2025 expand to three months.
  5. Pydantic validates the responseresponse_model checks and serializes the result to JSON.
  6. View stores raw data in refsResponses land in refs such as allOrders and inventoryItems. Totals, chart series, and rankings are computed properties derived from them.

Principles the code follows

  • Server owns filtering. The client never filters raw lists by warehouse or category itself; it re-requests.
  • Raw state in refs, derived state in computed. Keeps charts and KPIs consistent with a single source.
  • One API module. All HTTP calls live in client/src/api.js.
  • Data is ephemeral. JSON is read once at server start; restarting resets anything held in memory.
  • Inventory has no time dimension, so the month filter applies to orders only.

Known gaps

Found while reading the code. Worth knowing before you build on it.

  • Missing endpoints. api.js calls GET/POST /api/tasks, DELETE/PATCH /api/tasks/{id}, POST /api/purchase-orders and GET /api/purchase-orders/{id}. None of these routes exist in main.py, so those calls will return 404.
  • Purchase orders are empty. purchase_orders.json holds no records, so has_purchase_order is always false. The PurchaseOrder models are defined but unused by any route.
  • Hard-coded API URL. API_BASE_URL in api.js is http://localhost:8001/api, with no environment-based config.
  • Demo-grade security. No authentication, and CORS allows every origin. The user profile is a mock object in useAuth.js.
  • Duplicated quarter logic. /api/reports/quarterly re-implements the month-to-quarter mapping instead of using QUARTER_MAP.
